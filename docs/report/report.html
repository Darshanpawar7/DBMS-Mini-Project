Appendix A — Running the project

1. Problem statement and motivation

Students collect a large amount of material over a semester — lecture notes, PDFs, cheat sheets, past-paper solutions — but it ends up scattered across Drive folders, WhatsApp groups and laptops. Every one of those tools searches by exact keywords or file names. A student who wants "notes that explain how a model decides which words matter" finds nothing unless someone happened to use those words; the note titled Transformers and Self-Attention Explained stays invisible.

Finding study partners is just as ad hoc: students ask around in class groups, with no way to see who is actually working on the same topics.

ScholarMesh addresses both problems with one database design. Students upload notes; the text is split into passages and turned into embeddings (lists of 384 numbers that capture meaning), so a question finds notes by meaning, not by wording. The same embeddings, averaged over what each student uploads, saves and searches for, form an interest profile that the database uses to recommend study groups and classmates. Course enrollment and a three-level visibility rule (public / course-only / private) decide what anyone is allowed to see.

Why this is more than CRUD. Retrieval is by vector similarity and full-text ranking, not WHERE title LIKE …; access control is enforced inside every query path by one database function; group matching combines relational facts (enrollment, membership) with vector similarity; and business rules such as seat limits and admin hand-over are enforced by triggers that also hold under concurrent requests.

2. Objectives

  1. Design a normalised relational schema for users, courses, notes, tags, study groups and activity, and evolve the Phase 1 design with ALTER where Phase 2 needs more.
  2. Store note embeddings in a vector store (pgvector) linked to the relational data with real foreign keys, and retrieve notes by cosine similarity through an HNSW index.
  3. Offer three search modes — keyword (full-text), semantic (vector) and hybrid (rank fusion) — that all respect the same access-control rule.
  4. Recommend study groups and partners from enrollment plus interest-vector similarity.
  5. Enforce data integrity in the database itself: constraints, triggers, transactions, row locks and a least-privilege application role.
  6. Provide a Next.js web application with authentication and two system roles (student, admin) that talks to the database only through a server-side API layer.
  7. Verify the result with automated unit, database-integration and end-to-end tests.

3. Scope

In scope

  • Registration, login, logout; roles student and admin; per-group roles admin/member
  • Uploading PDF, TXT and Markdown notes (or pasted text); text extraction; chunking; embedding
  • Keyword, semantic and hybrid search with course/tag filters; search history
  • Library browsing with filters, sorting and pagination; bookmarks; "more like this"
  • Course enrollment; study groups (create, join, leave, manage members); recommendations
  • Admin: analytics dashboard, user roles and deactivation, course catalogue, tag merging, audit log, embedding job

Out of scope

  • Scanned PDFs (OCR) and images inside documents
  • Real-time chat inside study groups; notifications by e-mail
  • Password reset by e-mail and single sign-on
  • Horizontal scaling (the login rate limiter and embedding model run in one server process)
  • Verified enrollment. Students enroll themselves, so "course-only" means "visible to anyone who enrolled in the course". In production ENROLLMENT would be synced from the university's student information system or protected by per-course join codes.

7. ER-to-relational mapping and relational schema

Mapping rules: every strong entity becomes a table with its key; a 1:N relationship puts the foreign key on the N side; every M:N relationship becomes a junction table whose primary key combines both foreign keys and which carries the relationship's attributes; the weak entity DOC_CHUNK takes its owner's key (doc_id) — its identity is (doc_id, chunk_index), enforced as UNIQUE, with a surrogate chunk_id for convenient references.

Underlined = primary key, italic = foreign key. Referential actions: deleting a student cascades to their documents, bookmarks, memberships and searches, but sets STUDY_GROUP.created_by and AUDIT_LOG.actor_id to NULL; deleting a course sets DOCUMENT.course_id to NULL (a trigger turns course-only notes private) and cascades to its enrollments and groups.

Normalisation. Every non-key attribute depends on the whole key and nothing but the key: multi-valued facts (tags, enrollments, bookmarks, memberships) live in junction tables; course details are not repeated in documents or groups. The only derived values are deliberate and maintained by the database — the generated search_tsv and the materialized view used for analytics — so the schema is in BCNF.

8. Database choice and justification

DataStored inWhy
Users, courses, enrollments, groups, memberships, bookmarks, tags, search history, audit trailPostgreSQL tables Highly structured with many relationships; integrity matters (a membership must reference a real student, group and enrollment); needs transactions and row locks (two students joining the last seat).
Note text and its full-text indexPostgreSQL TEXT + generated tsvector + GIN Exact-term search with stemming and ranking, kept in sync automatically by a generated column.
Passage embeddings, query embeddingspgvector vector(384) + HNSW index Notes are unstructured; meaning-based retrieval needs nearest-neighbour search over vectors, which a B-tree cannot do.

Why pgvector rather than a separate vector database

  • One query can combine both paradigms. The access rule (enrollment, visibility, ownership) and the vector ranking run in the same SQL statement, so a private note can never "leak" through the vector store. With an external store the app would have to fetch nearest neighbours first and filter afterwards.
  • Real referential integrity. DOC_CHUNK.doc_id is a foreign key with ON DELETE CASCADE; deleting a note deletes its vectors in the same transaction. Phase 1's string pointer could dangle.
  • Transactions span both. Re-chunking after an edit and marking the document pending happen atomically.
  • Vectors become SQL values. AVG(embedding) builds document centroids and student interest vectors inside views — the basis of group matching.
  • Operationally simple. One Docker container, one backup, one connection pool.

The trade-off is scale: a dedicated vector database is better beyond tens of millions of vectors. For a university's notes (thousands of documents) PostgreSQL with HNSW answers in milliseconds.

10.2 Validation and integrity inside the database

  • 25 CHECK constraints, e.g. e-mail format, password must be a bcrypt hash (a plain-text password is impossible to store), semester format YYYY-ODD|EVEN, tag format, file type and size, group size 2–20, course-only visibility needs a course.
  • Keys: 12 primary keys (4 composite), 15 foreign keys with deliberate CASCADE / SET NULL actions, unique constraints (course code, tag name, group name per course, chunk position) and a case-insensitive unique index on e-mail.
  • Triggers normalise input (names, e-mails, tags) before CHECKs run and enforce cross-table rules a CHECK cannot express (§10.6).
  • The API validates the same rules first (zod) for friendly field messages; the database is the final authority.

10.7 Transactions and concurrency

  • Upload: BEGIN → insert DOCUMENT (T4 writes chunks) → upsert tags → link tags → COMMIT. Any failure rolls everything back and the API deletes the stored file, so no orphan rows or files remain.
  • Join a group: CALL sp_join_group locks the group row with SELECT … FOR UPDATE. Two students racing for the last seat are serialised — one succeeds, the other receives SM001. This is proven by an automated test that opens two connections and runs both joins at the same time (§16).
  • Leaving and member changes: CALL sp_leave_group, and the promote/remove endpoints, lock the same group row first. Without it, the last two members leaving at the same instant could each see the other still present and leave an empty group with no admin; with it the second leave sees the first and deletes the group (also proven by a two-connection test).
  • Audit attribution: every write transaction runs SELECT set_config('app.current_user_id', $1, true); the setting is local to the transaction, so the audit trigger always records the right user even with pooled connections.
  • All writes that change several rows (admin role changes, deleting courses or users, leaving groups) run inside withTransaction().

10.8 Database security

  • Two logins: postgres (owner, used only by the setup script) and scholarmesh_app (used by the web app) with SELECT/INSERT/UPDATE/DELETE + EXECUTE only — it cannot create, alter or drop objects (tested: error 42501).
  • AUDIT_LOG is append-only for the app role (UPDATE/DELETE/TRUNCATE revoked).
  • Passwords: bcrypt (cost 10) in the app, enforced by a CHECK; all credentials come from environment files that are not committed.
  • Every SQL statement in the app is parameterised ($1, $2 …); no SQL is built from user input.

11. Vector database and semantic search

What is embedded(a) every passage of every note — the text is split by trigger T4 using fn_chunk_text into chunks of at most 800 characters (paragraphs kept together, long paragraphs split on sentence boundaries); (b) every search query, stored in SEARCH_LOG.query_embedding for interest profiles.
Modelsentence-transformers/all-MiniLM-L6-v2 (ONNX, 8-bit quantised), run locally in Node.js with Transformers.js — no API key and no note text leaves the server. Mean pooling + L2 normalisation → 384-dimensional unit vectors. Chosen after comparing three 384-d models on sample questions: it gave the clearest gap between relevant and unrelated notes.
StorageDOC_CHUNK.embedding vector(384) (pgvector), NULL until the embedding worker fills it; DOCUMENT.embedding_status tracks pending → ready (or failed).

Hybrid search — Reciprocal Rank Fusion

Keyword search is precise for exact terms ("BCNF"); semantic search understands paraphrases. fn_hybrid_search runs both and merges them with Reciprocal Rank Fusion: score = 1/(60 + keyword_rank) + 1/(60 + semantic_rank) (a missing rank contributes 0). A note found by both methods rises to the top; a note found by only one still appears. Example: "bcnf decomposition" returns nothing in keyword mode (no note contains "decomposition") but the normalization note in semantic and hybrid mode (Figures 5–6).

Interest profiles and study-group matching

v_doc_centroid averages each document's passage vectors. v_student_interest averages, per student, the centroids of notes they uploaded or bookmarked and the vectors of their searches from the last 120 days. A group's interest is the average of its members' interest vectors. fn_recommend_groups considers only groups in the student's courses that still have a seat and ranks them by

match = 0.7 × cosine(student interest, group interest) + 0.3 × Jaccard(student topics, group topics)

where "topics" are the tags of notes each person uploaded or bookmarked within that group's course. fn_recommend_partners ranks classmates (students sharing a course) by interest similarity.

Embedding pipeline

  1. Upload: one transaction inserts the DOCUMENT; trigger T4 writes its DOC_CHUNK rows (no vectors yet); tags are linked.
  2. After commit the API embeds the new chunks in one batch and writes them with a single set-based UPDATE … FROM unnest(…); the document becomes ready.
  3. If the model is unavailable the note is still saved and keyword-searchable (failed); an admin re-runs the job later. Editing the text re-chunks it and resets it to pending.

14. System architecture

Request flow (example: a semantic search)

  1. The browser calls GET /api/search?q=…&mode=semantic with the session cookie.
  2. proxy.ts only checks that a validly signed cookie exists; the route handler re-reads the user from STUDENT (role, is_active) and validates the query with zod — so deactivation, deletion and promotion take effect immediately.
  3. The server embeds the question with the local model (cached for repeated questions).
  4. One SQL statement calls fn_semantic_search, which applies fn_visible_doc_ids and the HNSW index, and joins v_document_catalog for display fields.
  5. The query and its vector are written to SEARCH_LOG (analytics and interest profile); results return as { ok, data }.

Application security

  • bcrypt password hashes; constant-cost login (a dummy hash is checked for unknown e-mails); 10 attempts per 15 minutes per account, plus per-IP limits when a trusted reverse proxy supplies the address (a client-sent X-Forwarded-For is never trusted).
  • Session: HS256 JWT in an httpOnly, SameSite=Lax cookie (Secure in production); role and active flag re-read from the database on every request.
  • CSRF: every POST/PATCH/DELETE must come from the same origin. XSS: React escapes output; search highlights use markers that are turned into <mark> elements, never injected as HTML.
  • Uploads: body size checked before parsing (5 MB), extension whitelist, PDF magic-byte check, at most 150 pages and 300 000 characters, 30 uploads per hour per user, random server-side file names (no path traversal).
  • Private notes never leak through aggregates: tag lists, trending topics, course note counts, interest profiles and group matching all count only notes the viewer may see. Group pages are visible only to members, students of the course and admins.
  • Security headers (X-Frame-Options, nosniff, Referrer-Policy, Permissions-Policy); generic 500 messages, details only in server logs.
  • Configuration only through environment variables, validated at start-up (DATABASE_URL, AUTH_SECRET ≥ 32 chars).

19. Conclusion and future enhancements

ScholarMesh shows how one PostgreSQL database can serve two paradigms at once: a strictly validated relational model for people, courses, groups and activity, and a vector store for meaning-based retrieval — joined in single SQL statements so that access control, ranking and integrity are guaranteed by the database rather than by application code. Phase 1's design was corrected (redundant and missing indexes, a dangling vector pointer, a destructive cascade, missing roles and rules) and extended with chunk-level embeddings, full-text search, views, a materialized view, stored functions and procedures, triggers, an audit trail and a least-privilege application role. A Next.js application exposes all of it through a validated API, and 101 automated tests confirm the behaviour, including real races for the last seat in a group and for leaving one.

Future enhancements

  • OCR for scanned PDFs and handwritten notes; image and diagram embeddings.
  • Verified enrollment — sync ENROLLMENT from the university system, or require a per-course join code.
  • Row-Level Security policies so the access rule is enforced even for ad-hoc SQL, not only through the functions.
  • Background job queue (e.g. a worker table polled with SELECT … FOR UPDATE SKIP LOCKED) for large uploads.
  • Re-ranking the top hybrid results with a cross-encoder; per-course embedding fine-tuning.
  • Notifications when a recommended group has a free seat; meeting scheduling inside groups.
  • Table partitioning of SEARCH_LOG and AUDIT_LOG by month as they grow; a Redis-backed rate limiter for multiple servers.
